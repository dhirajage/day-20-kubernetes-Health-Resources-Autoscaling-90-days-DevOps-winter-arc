01 / Core Concepts: Probes, Resources, QoS & HPA

Section 01 / Concepts

Kubernetes Health & Scaling Mechanisms

  • Startup Probe: Validates if the application has started; delays liveness and readiness checks until successful.
  • Liveness Probe: Checks if the container is healthy; failure triggers a container restart based on restart policy.
  • Readiness Probe: Determines if the Pod can accept traffic; failure removes the Pod from Service endpoints.
  • Requests & Limits: Requests guarantee minimum compute resources for scheduling; limits cap resource consumption.
  • Quality of Service (QoS): Classified into Guaranteed, Burstable, and BestEffort based on resource specs.
  • Horizontal Pod Autoscaler (HPA): Automatically scales replica count dynamically based on observed CPU utilization metrics.

Essential kubectl Commands for Day 20

  • kubectl top nodes — View node-level CPU and memory consumption
  • kubectl top pods -n day20-health — Monitor active pod resource metrics
  • kubectl autoscale deployment... — Configure HPA targets and replica bounds
  • kubectl get hpa -n day20-health -w — Watch autoscaling adjustments live
  • kubectl run load-generator... — Generate synthetic CPU load using Busybox
  • kubectl describe pod... — Inspect container lifecycle events and probe statuses

12 / Interview Readiness & Architecture Q&A

Section 13 / Interview Q&A

1. Readiness vs Liveness Probes?

  • Readiness decides if a Pod receives traffic; liveness detects stuck containers and triggers restarts.

2. Why use a Startup Probe?

  • It gives slow-starting applications time to initialize before liveness and readiness checks take over.

3. Why does HPA need CPU requests?

  • CPU utilization is measured relative to requested CPU; without requests, utilization percentage is undefined.

4. Explain QoS Classes in K8s.

  • Guaranteed: Equal requests/limits. Burstable: Requests set, unequal limits. BestEffort: No requests/limits.
